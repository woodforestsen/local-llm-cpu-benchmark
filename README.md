# CPU 上跑本地大模型：量化、线程与质量的实测对比

在一台 **18 逻辑核的 Windows 机器（无独显）** 上，实测三个细节：

1. 把量化等级从 **Q4_K_M 提到 Q8_0**，速度和质量各付出多少、换来多少？
2. **线程数加到多少就不再提速**？生成和预填充的瓶颈一样吗？
3. 持续跑会不会降频，导致测量结果不可信？

所有数字都是本机跑出来的，脚本和原始数据都在这个目录里。

---

## 结论先行

| # | 结论 | 证据 |
|---|---|---|
| 1 | **在这台机器上，Q4_K_M 完胜 Q8_0** | Q8_0 体积 +57%、预填充慢 38.6%、生成慢 17.0%，而客观题得分**一分没涨**（9/11 vs 9/11） |
| 2 | **生成速度约 12 线程触顶，预填充到 18 线程仍线性增长** | 生成是内存带宽瓶颈，预填充是算力瓶颈 |
| 3 | **持续满载会降频，破坏测量** | 同一配置（16 线程 Q4_K_M）冷机 17.32 tok/s，连续负载 30 分钟后只有 12.31 tok/s |
| 4 | **CPU 上优化推理的正确方向是量化，不是加线程** | 12 线程后再加线程，生成速度只涨 5% |

## 测试环境

| 项目 | 值 |
|---|---|
| CPU | 18 逻辑核 |
| 内存 / 磁盘 | D: 57.5 GB 可用，E: 179.9 GB 可用 |
| GPU | 无（纯 CPU 推理） |
| 运行时 | Ollama 0.32.15 |
| Python | 3.13 |

**测试方法**：输入长度约 1294 token，生成 128 token，温度 0、固定随机种子，每档跑 3 次取中位数（线程扫描取 best-of-5）。

## 一、量化对比（16 线程）

| 模型 | 大小 | 预填充 pp (tok/s) | 生成 tg (tok/s) | 客观题得分 |
|---|---|---|---|---|
| **qwen3:1.7b (Q4_K_M)** | 1.4 GB | **180.04** | **17.32** | **9/11 (81.8%)** |
| qwen3:1.7b-q8_0 | 2.2 GB | 110.56 | 14.38 | 9/11 (81.8%) |
| qwen3-lora:latest | 639 MB | 257.58 | 25.00 | — |

**Q4_K_M → Q8_0 的代价与收益**

| 维度 | 变化 |
|---|---|
| 模型体积 | **+57%**（1.4 → 2.2 GB） |
| 预填充速度 | **−38.6%**（180.04 → 110.56） |
| 生成速度 | **−17.0%**（17.32 → 14.38） |
| 客观题得分 | **±0**（9/11 → 9/11） |

> 结论：在这台纯 CPU 机器上，Q8_0 是明确的亏本买卖。CPU 推理本来就受内存带宽限制，权重体积直接等于速度；而 1.7B 这个量级的模型，Q4_K_M 的精度损失在简单任务上测不出来。
>
> **注意**：这不代表 Q8_0 没用。任务变难（长链条推理、代码、数学）之后差距可能出现——所以结论要限定在"这批题、这个模型尺寸"上。

## 二、线程数扫描（qwen3:1.7b Q4_K_M，best-of-5）

| 线程 | 预填充 pp (tok/s) | 生成 tg (tok/s) | 相对最快 |
|---|---|---|---|
| 4 | 70.3 | 8.73 | 66% |
| 8 | 104.5 | 11.39 | 87% |
| **12** | **137.64** | **12.49** | **95%** |
| 16 | 155.99 | 12.31 | 94% |
| 18 | 157.9 | 13.16 | 100% |

**两条曲线的形状完全不同，这才是重点：**

- **生成速度**：4 → 8 提升最大，**12 线程之后基本到顶**（12/16/18 挤在 94–100%）
- **预填充速度**：一路线性涨到 18 线程（70 → 158），**完全没到顶**

**为什么**：生成一个 token 需要把整个模型的权重读一遍，速度由**内存带宽**决定，加核心没有用；预填充是矩阵乘法，是纯**算力**活，能吃满所有核心。

**实践含义**：
- 想让生成变快 → **降量化**（减少每 token 的读取量），不是加线程
- 想让长文档处理变快 → 加线程 / 换更好的 CPU
- 12 线程是这台机器的性价比拐点，再往上收益很小

### 补充：同一配置冷机重测，快出 75%

第一轮 q8_0 的曲线出现了"8 线程比 18 线程快 28%"的反常现象。怀疑是热降频，于是**让机器冷却后单独重测**：

| 线程 | 冷机重测 tg | 连续负载后 tg | 差异 |
|---|---|---|---|
| 4 | 12.02 | 6.97 | +72% |
| 8 | 14.95 | 14.91 | ~0 |
| **12** | **20.29** | 11.57 | **+75%** |
| 16 | 16.67 | 11.44 | +46% |
| 18 | 17.02 | 11.63 | +46% |

**结论**：上一组数字被系统性压低了约 40%，反常现象消失（12 线程成为峰值，与 Q4_K_M 的拐点一致）。

**这带来一条比数字本身更重要的方法学结论**：同一台机器、同一配置，**不同时段跑出的绝对值能相差 40%**。所以：

- **跨时段对比是无效的**——"今天 Q8 比昨天 Q4 快"这种结论毫无意义
- 只有**同一时段内、控制机器状态（冷却 + 无后台负载）**的数据才能横向比较
- 跨模型的绝对速度对比，最好在同一轮测试里交替跑，而不是先跑完 A 再跑 B

## 三、被测量方法坑过的三次（这部分最值钱）

这三件事本身就能在面试里讲很久——**它们证明的不是"我会跑脚本"，而是"我知道数字什么时候是假的"**。

### 坑 1：Ollama 的前缀缓存让速度虚高 130 倍

第一次跑出来是 **32405 tok/s**。CPU 上不可能。原因是 Ollama 有前缀缓存：提示词完全一样时，第二次的「输入处理」直接命中缓存，耗时趋近于零。

**修法**：每次在提示词**最前面**加一个变化的短标记，强制重新计算。

```
32511 → 180.04 tok/s   （Q4_K_M 预填充，16 线程）
32405 → 246.84 tok/s   （qwen3-lora）
```

> 如果没发现这个，简历上写"32405 tok/s"，面试官一句话就问穿。

### 坑 2：Qwen3 的思考模式吃光 token，质量分全错

第一轮质量测试得分：Q4_K_M **45.5%**、Q8_0 **27.3%** —— 8 位量化反而更差，违反常识。

翻出原始回答发现：**需要"想一下"的题，答案栏全是空的**。因为 Qwen3 默认先输出一大段思考过程，256 个 token 的额度被推理吃光，正式答案还没开始就截断了。

**修法**：请求里加 `"think": false`，并把额度提到 512。

修复后：**9/11 (81.8%) vs 9/11 (81.8%)** —— 反常现象消失，结论才可用。

### 坑 3：持续负载导致降频，同一配置差 29%

线程扫描第二轮里出现"8 线程比 18 线程快 28%"，物理上不可能。

原因：测试序列前半段跑 Q4_K_M、后半段跑 Q8_0，机器已连续满载 30 多分钟。旁证：单独跑 Q4_K_M 在 16 线程是 **17.32**，而扫描里同样配置只有 **12.31**。

**修法**：
- 每档取 **best-of-N**（干扰只会让结果变慢，不会变快，所以最快的那个最接近真实能力）
- 模型之间强制卸载，避免内存压力串扰
- **分批测、留冷却间隔**

## 复现方式

```bash
# 1. 拉模型（约 3.6 GB）
ollama pull qwen3:1.7b
ollama pull qwen3:1.7b-q8_0

# 2. 测速度
python bench_ollama.py

# 3. 测线程曲线
python thread_sweep.py

# 4. 测质量（20 题：5 事实 / 5 算术 / 5 写作 / 5 指令）
python quality_test.py
```

输出：`bench_results.csv`、`thread_sweep.csv`、`quality_results.csv`、`answers/`。

---

## 文件说明

| 文件 | 作用 |
|---|---|
| `bench_ollama.py` | 速度基准（pp / tg），含缓存规避 |
| `thread_sweep.py` | 线程数扫描，best-of-5，模型间卸载隔离 |
| `thread_sweep_q8.py` | 单独重测 Q8_0（验证降频假设） |
| `quality_test.py` | 20 题质量测试，客观题自动判分 |
| `answers/` | 每个模型的原始回答（主观题要人工抽检） |
| `bench_results.csv` | 速度原始数据 |
| `thread_sweep.csv` | 线程曲线原始数据（Q4_K_M + Q8_0）。**注意：其中 Q8_0 那 5 行是在持续负载之后测的，被降频压低了约 40%** |
| `thread_sweep_q8_cooled.csv` | Q8_0 **冷机**重测（`condition=cooled`），用来验证降频假设；和上面那份对照着看 |
| `quality_results.csv` | 质量得分 |
